# Founder manual discounts — build plan (phase 1)

**Spec:** [`2026-08-09-founder-manual-discounts-design.md`](../specs/2026-08-09-founder-manual-discounts-design.md)
**Parent design:** [`2026-07-15-discounts-design.md`](../specs/2026-07-15-discounts-design.md)

**Goal:** A founder can apply one fixed or percentage discount to an editable Ops quote, with a
mandatory reason, a 30% ceiling, a vehicle-minimum floor, and an append-only history of who, when, why, and
the price and margin either side of the decision.

**Architecture:** A pure arithmetic step inside the existing engine, between core pricing and
finishing, driven by a resolved instruction the route hands it. Persistence is one new
history-retaining table written in the same transaction as the quote save. No new pricing
implementation, no promotion matching, no website change.

**Tech Stack:** Node 20 · TypeScript (strict) · Hono · Zod · Drizzle + Postgres · Vitest · npm.

## Global Constraints

- **One task = one branch = one PR.** Build only what the task's Files list says.
- **Tests first, proven.** Write the failing test, run it red, implement to green, paste the
  red→green evidence in the PR. Task 1 is the exception and says so.
- `cd api && npm run check` green before every PR. `npm run test:all` too for Tasks 6–7.
- **Money is integer minor units.** No floats anywhere in this plan.
- **Never `git add -A`.** Multiple sessions share this working tree; stage by path.
- The flag `OPS_MANUAL_DISCOUNTS_ENABLED` defaults **off** and gates creation only. Reading an
  existing discount is unconditional from the moment the table exists.

## Preconditions — all met

**Revised 2026-08-09.** The cost-cap design (and with it the extras cost basis, which briefly
gated this plan) was replaced by the owner with a far simpler rule: **max 30% off the subtotal,
and the final total may not fall below the quote's vehicle fare floor.** No cost estimate is
involved, so there is nothing left to confirm. See spec §5.2–§5.3 for the reasoning — in short, a
per-km cost estimate understates a short trip badly, because the driver charges a fixed minimum
to take the job at all.

Tasks 1, 2 and 3 can all start. Task 1 is already done (`735eb85`).

## Scope decisions taken before writing this plan

Recorded so a reviewer does not re-litigate them:

1. **Manual only.** No promotion rules, no codes, no automatic matching, no `promotion_rules`
   table, no redemption budgets. Owner decision 2026-08-09.
2. **No `discount_events`.** `quote_discounts` is append-only and `quote_revisions` already
   stores per-revision totals. A third audit system waits for promotion lifecycle events.
   Spec §4.4.
3. **A discounted quote cannot mint a partial-leg pay link.** Fails closed. Parent §18.1
   option 1.
4. **Before/after totals and margins are stored, not computed.** Finishing runs after the
   discount, so the after-total is not derivable by subtraction, and margins must stay truthful
   after the rate card moves. Spec §4.2.
5. **The discount line item is tagged `meta.kind = 'discount'`** and `paySelection.ts` is taught
   to skip it, in the same PR. Parent §18.5 option 1.
6. **No website changes.** Phase 1 is Ops-only; customers see a discount only on surfaces that
   render a quote already discounted by a founder.

### Task 1: The zero-discount gate

**This task cannot fail first, and that is stated deliberately rather than dressed up as TDD.**
It commits fixtures asserting behaviour that already exists. Its value is as the regression guard
every later task is measured against, so it lands first and alone.

**Files:** `api/src/quote/fixtures/zeroDiscount.ts`, `api/src/quote/zeroDiscount.test.ts`

Expected values are **reviewed constants, hand-checked against a live `POST /quote`** — never
generated by the implementation under test.

Cover, at current values:

- Private: car and van, each below and above its floor. **Van minimum is $49.99** (PR #349) —
  any fixture carried over from before 2026-08-07 is wrong by a cent.
- Private multi-leg, and a leg carrying `via_stops`.
- Chauffeur: travel days, idle days, the buffer, and `travelKm` vs `billableKm`.
- Extras: each of the six codes, and an attributed per-leg extra.
- Finishing: charm, nearest-50, unchanged, and the protected-minimum floor. Assert the
  **two-limit** rule of 2026-07-26 — the `maxReductionBps` cap *and* `MAX_REDUCTION_CENTS` ($10)
  on the fixed $10 grid — not the superseded 2.5%-only behaviour.
- A partial-leg pay link at `sold_cents`, plus `payLines()` output for a private quote.

**Done when:** every fixture passes against today's code, and mutating any pricing constant makes
at least one fail.

### Task 2: Pure discount arithmetic

**Depends on:** Task 1 green. (The spec §5.3 pricing assumption is owner-approved — no gate here.)

**Files:** `api/src/quote/discount.ts` (+ test), `api/src/quote/engine.ts`,
`api/src/quote/paySelection.ts`

**Interfaces:**

```ts
export type DiscountRequest =
  | { source: 'manual'; method: 'fixed'; amountCents: number; reason: string }
  | { source: 'manual'; method: 'percentage'; basisPoints: number; reason: string };

export interface ResolvedDiscount {
  method: 'fixed' | 'percentage';
  value: number;
  requestedCents: number;
  appliedCents: number;
  eligibleSubtotalCents: number;
  capReason: 'percentage_cap' | 'vehicle_minimum' | null;
}
```

`quote()` gains an optional third parameter. Omitted, **every existing code path is
byte-identical** — that is what Task 1 proves.

Implement per spec §5.2 — and note how much smaller this is than the original draft:

```ts
const percentageCap = Math.floor(subtotalCents * 30 / 100);
const floorHeadroom = Math.max(0, subtotalCents - protectedMinimumCents);
const appliedCents  = Math.min(requestedCents, percentageCap, floorHeadroom);
```

`protectedMinimumCents` is already computed at `engine.ts:58` as
`rides.length * rateCard.floorCents[vehicle]` — one driver minimum per leg. **Read it; do not
recompute or hardcode floors**, so the rule tracks the rate card. It is `0` for chauffeur, which
correctly leaves chauffeur bounded by the 30% cap alone.

No cost estimate, no extras cost basis, no `discount_cost_unavailable`. Shared is rejected before
arithmetic runs.

Emit one line item `{ amountCents: -appliedCents, meta: { kind: 'discount' } }` after the extras
and before the finishing item.

`engine.ts:123` currently reads:

```ts
finishPrice(subtotalCents, Math.max(costCents, protectedMinimumCents), rateCard.priceFinishing)
```

**One change, and only on the discounted path:** `rawCents` becomes the **discounted** subtotal.
That is all. It is easy to miss because the variable name does not change.

**Leave the second argument alone.** An earlier draft of this plan changed it to `costCents` so a
founder could cross the fare floor — that is now exactly backwards, since the floor is the
protection. Nothing needs changing there anyway: `appliedCents` is already capped at
`floorHeadroom`, so the discounted subtotal is `>= protectedMinimumCents` before finishing sees
it, and `finishPrice` never returns below its minimum. The floor holds through finishing for free.

Subtotal and floors both come from the quote's **locked** rate card where one exists (spec §6.1),
never the live card — `rateCardFor()` hands back the live card once `rate_locked_until` has
passed, and the limit must not follow it.

**In the same PR**, extend `paySelection.ts`'s filter to skip `meta.kind === 'discount'` as it
already skips `price_adjustment`. Test that a discounted private quote's `extraIndexes` still
align one-for-one with `engine.extras`, and that `payLines()` never returns a negative line.

**Done when:** discount arithmetic tests are green, Task 1's fixtures are untouched and still
green, and no DB, route, RBAC, or UI file was modified.

### Task 3: `quote_discounts` — table and repositories

**Depends on:** nothing. Can run in parallel with Tasks 1–2.

**Files:** `api/drizzle/0043_quote_discounts.sql`, `api/src/db/schema.ts`,
`api/src/db/quoteDiscountRepo.ts`, `api/src/db/postgresQuoteDiscountRepo.ts` (+ tests)

**Write the migration by hand.** This repo's drizzle snapshots stop at `0028_snapshot.json` —
**do not run `npm run db:generate`.** Follow `0042_booking_legs.sql` and add the journal entry;
the journal's `when` is a high-water mark, not a clock.

Columns exactly per spec §4.1. Constraints:

- Partial unique index: one `status = 'active'` row per `quote_id`.
- Non-negative checks on every money column.
- `reason` and `applied_by` NOT NULL. `estimated_cost_cents` and the two margin columns are
  **reporting only** and nullable — the cap no longer reads them (spec §5.2), and the engine
  returns a null margin for shared.
- `quote_revision` is a plain integer stamp with **no foreign key**: `quote_revisions` holds only
  superseded states, so the live revision has no row to reference.

Repository exposes `apply`, `supersede`, `activeFor(quoteId)`, `historyFor(quoteId)`. The
in-memory fake implements the identical contract — every later task tests against the fake.

**Contains a migration.** Merging it to `main` releases it to staging on boot. It is additive and
nullable; no existing row changes. Flag it in the PR description.

**Done when:** migration applies and rolls back cleanly, both repo implementations pass the same
suite, and the active-row uniqueness is proven by a failing concurrent insert.

### Task 4: Atomic quote-save + discount transaction

**Depends on:** Tasks 2 and 3.

**Files:** the quote save path in `api/src/db/` (+ tests)

One Postgres transaction covering: quote content, `revision` increment, `quote_revisions` row,
and the `quote_discounts` apply-or-supersede. Mirror the existing conversion-transaction pattern
in `postgresQuoteConversionRepo.ts`.

**Tests:** an injected failure at each write point rolls back **all** of them; a discount applied
to a quote that then fails to save leaves no orphan row; replace and remove write complete
history in one transaction.

**Done when:** no partial state is reachable under injected failure. No route or UI change.

### Task 5: Ops API — capability, tri-state intent, history

**Depends on:** Task 4.

**Files:** `api/src/routes/internalQuote.ts`, `api/src/lib/opsAuth.ts` (+ tests)

Add `discount:apply_manual`, founder-only. **Do not add `promotion:manage`** — nothing manages.

Extend estimate/save with an optional `discount` field:

- **omitted** → preserve the active discount
- **request** → founder-only add or replace
- **`null`** → founder-only removal

Estimate stays side-effect free. Save uses Task 4's transaction. Any discount change invalidates
prior approval, exactly as a price-input change does.

Add `GET /internal/quotes/:id/discounts`, mirroring the existing `/:id/revisions` endpoint.
Strip `estimated_cost_cents`, `margin_*` and `cap_reason` for anyone without `margin:view`,
using the existing `stripQuoteMargin()` pattern — **including nested inside a stored quote
result**, which is where the existing leak tests already live.

**Refuse the pay-link mint** when an active discount exists: `409 not_linkable`, alongside the
existing refusals at `internalQuote.ts:1006–1021`.

**Tests:** founder/finance/ops/system matrix on every verb; CSRF; tri-state semantics; approval
invalidation; leak tests on both projections; the pay-link refusal; gated behind
`OPS_MANUAL_DISCOUNTS_ENABLED` with the flag off proving no creation path exists.

### Task 6: Ops UI

**Depends on:** Task 5. Runs `npm run test:all`.

**Files:** `api/src/routes/ops-ui.html` (+ Playwright)

- Founder-only enabled controls: fixed/percentage toggle, value, **required** reason, apply,
  replace, remove. Other roles see a read-only discount row.
- Requested-vs-applied display when either limit bit, naming which one, with the founder-only margin.
- Derived `Discounted` badge on queue and detail — from `discountCents > 0`, not a status.
- A discount history panel, reusing the version-history panel's shape and its endpoint pattern.
- **The outstanding-pay-link warning** (spec §6.3): applying, replacing, or removing a discount
  bumps `revision` and kills every live pay link. Warn before the action, naming the consequence.
- Generated WhatsApp/email drafts show the friendly discount row and never the finishing line,
  cost, or margin. The existing generated-message basis hash covers staleness.

**`ops-ui.html` is the hot file** — nearly every open PR touches it. Merge smallest-first and use
update-branch; watch for conflicts where neither side alone is right.

**Gate:** desktop and mobile Playwright; role tests proving non-founders cannot mutate via the
API even with the controls hidden; no unrelated Ops layout change.

### Task 7: Carry the discount into the booking, and render it

**Depends on:** Task 6.

**Files:** `api/src/quote/quoteToBooking.ts`, `api/src/db/quoteConversionRepo.ts`,
`api/src/quote/customerQuoteView.ts`, `api/src/routes/quoteView.ts`, `quoteCard.ts`,
`payCard.ts`, `shareCard.ts` / `shareCardImage.ts`, `quotePay.ts`

**Attach the snapshot in `quoteToBooking`, not in one caller.** There are three conversion
paths and all three funnel through it:

| Path | Caller | Used by phase 1? |
| --- | --- | --- |
| Ops "mark booked" | `internalQuote.ts:898` | **Yes** |
| Pay link | `quotePay.ts:272` | **Yes** |
| Web quote v2 | `quoteConversionRepo.ts:115` | No — phase 2 |

`bookings.subtotal` / `discount_total` / `pricing_snapshot_json` are today written **only** by
`POST /bookings/from-quote-v2` (see the comment at `schema.ts:35`) — the one path a phase-1
discounted quote never takes. Writing the discount in `quoteConversionRepo` alone would produce
a booking with no discount record for the actual Ops flow. Put it in `quoteToBooking` so every
path inherits it, then let `quoteConversionRepo.ts:169` stop hard-coding `discountTotalCents: 0`.

The pay-link path is reachable only for an **undiscounted** quote (Task 5 refuses the mint
otherwise), so its discount total is always zero — but it must go through the same code, so the
refusal is the only thing keeping it zero and a future change cannot silently produce a wrong
booking.

Then render the stored discount row on every surface that shows a quote or booking total. No
surface recalculates. The internal finishing line stays hidden, as today.

**The share card renders money into a PNG** — assert the rendered figure, not just the data
handed to the renderer. A wrong number there cannot be corrected by a reload and is the surface
most likely to be forwarded.

**Tests:** a discounted Ops quote converted via **mark-booked** lands `subtotal`,
`discount_total` and `pricing_snapshot_json` on the booking — this is the phase-1 path and the
one the original draft of this plan missed; independent fixtures per surface, all agreeing to the
cent with the stored snapshot; LKR locked-FX display; checkout, payment and webhook amounts equal
to the booking snapshot; legacy no-discount quotes unchanged on every surface, with
`discount_total` still null.

## Self-Review

**Spec coverage:** §3.1 → Tasks 2, 5, 6; §4 → Task 3; §5 → Task 2; §6 → Tasks 4, 5; §6.1 → Task 2; §6.3 →
Task 6; §7 → Task 5; §8 → Task 5; §10 → Task 1 plus per-task suites; §11 → Tasks 3–7.

**Not covered here, by design:** everything in the parent spec's §7.1, §7.4, §7.6, §11.1, §11.3,
§12.1, §12.3, §13.1, §13.2 and §18.2–18.4. That is phase 2 and needs the owner decisions the
parent §18 records.

**Deliberate deviation from the parent spec, restated for a reviewer:** the parent's §6 puts the
discount line item before the finishing item with no tag. This plan tags it
`meta.kind = 'discount'` and changes `paySelection.ts` in the same PR, because the untagged
ordering corrupts partial pay links on a shipped, customer-facing money path. Parent §18.5
records the reasoning and the two rejected alternatives.

**Sequencing:** Tasks 1 and 3 are independent of each other and of everything else, so they run
in parallel. Task 2 needs Task 1's fixtures green to prove the no-discount path is untouched.

**Type consistency:** `DiscountRequest` is the only shape a route accepts — clients never submit
applied cents, cost, margin, or an override flag. `ResolvedDiscount` is what the engine consumes.

**There is a mapping layer, and Task 4 owns it.** `ResolvedDiscount` carries `requestedCents`,
`appliedCents`, `eligibleSubtotalCents` and `capReason`, but **not** `total_before_cents`,
`total_after_cents`, `margin_before_cents` or `margin_after_cents` — those come from the
`QuoteResult` either side of the priced call, and `estimated_cost_cents` comes from the engine's
cost figure (reporting only — the limits never read it). Task 4 assembles the row from both. Test the assembly directly rather than assuming the
shapes line up; an earlier draft of this plan claimed they did, and they do not.

**Known gaps, accepted for phase 1:** concurrent quote edits can lose an update (spec §6.2) —
`revision` is a counter, not a concurrency token, and the proper fix is parent M20.2 in phase 2.
